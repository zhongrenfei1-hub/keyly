# Keyly

数字商品自助售卖站：买家下单付款后自动发卡密，后台管商品、卡密库存、订单、兑换码和工单。

一个 Next.js 应用加一个 SQLite 文件，不需要另装数据库。

## 本地运行

需要 Node 22.13 或更高（用到了 Node 自带的 `node:sqlite`）。

```bash
npm install
cp .env.example .env.local   # 然后填 ADMIN_PASSWORD 和 SESSION_SECRET
npm run seed                 # 可选：放 6 件示例商品，卡密是 DEMO- 开头的假数据
npm run dev                  # http://localhost:3210
```

- 店铺：<http://localhost:3210>
- 后台：<http://localhost:3210/admin>，密码是 `.env.local` 里的 `ADMIN_PASSWORD`
- 自检：`npm test`（下单锁库存、防重复发货、金额校验、超时释放、补发、兑换码、换号、站外付款链接、每周对账）

## 上线

```bash
npm run build
ADMIN_PASSWORD=... SESSION_SECRET=... SITE_URL=https://你的域名 npm start
```

上线前要做的事：

1. **上 HTTPS。** 生产环境的登录状态只通过 HTTPS 发送，没有证书后台登不进去。
2. **让买家能付款。** 模拟支付在生产环境默认是关的。要么接一个真实的支付渠道，要么给商品填「站外付款链接」，让买家到链动小铺这类平台付款。两种做法都在下面。
3. **设置 `SITE_URL`。** 支付回调地址靠它来拼。
4. **备份 `data/` 目录。** 订单和卡密都在 `data/keyly.db` 里，这个文件丢了就全丢了。
5. **删掉示例商品。** 如果跑过 `npm run seed`，在后台把带「示例」的商品删掉。
6. 前面有 Nginx 之类的反向代理时，让它覆盖 `X-Forwarded-For`，限流是按这个头里的 IP 算的。

数据库是单个文件，所以要部署在有持久磁盘的机器上（普通 VPS 就行），不适合 Vercel 这类无状态平台。

## 订单是怎么走的

1. 买家下单：建一笔「待付款」订单，同时锁定对应数量的卡密，保留 15 分钟。
2. 付款成功：支付平台通知 `/api/pay/notify/<渠道>`，验签、核对金额后把订单改成「已发货」，卡密显示在订单页。同一笔订单重复通知不会重复发货。
3. 超时没付：订单关闭，卡密放回库存。
4. 订单关闭后钱才到、库存又被别人买走：订单记为「已付款，待发货」。后台给这件商品导入卡密时会按付款先后自动补发。

买家没有账号。下单的浏览器可以直接看订单；换了设备要用「订单号 + 下单邮箱」验证一次。

## 接一个真实的支付渠道

1. 在 `src/lib/payment/` 里新建一个文件，照 `index.ts` 里的 `PaymentProvider` 接口实现四样东西：
   - `enabled()`：配置齐了才返回 `true`
   - `createPayment(order, urls)`：去支付平台下单，返回买家要去的付款地址
   - `parseNotify(req)`：校验通知的签名，返回订单号、实付金额、平台流水号
   - `ack`：平台要求的应答文本
2. 把它加进 `index.ts` 的 `ALL` 数组。

别的地方不用改：商品页会自动多出这个支付方式，通知入口、金额核对、发货都是现成的。`mock.ts` 是一个完整的例子。

## 用链动小铺这类寄售平台收款

链动小铺（ldxp.cn，现在的地址是 wzyp.cn）没有给外部网站用的通用开放接口。2026-11-14 查到的情况：

- 官网和商家后台都没有开发文档，后台菜单里也没有接口、密钥这一类设置。
- 网站和它网页自己用的内部接口都挂着人机验证（滑块），服务器直接请求只会拿到验证页；买家的下单页还带着按浏览器做的风控。所以本站不去那边同步商品、代下订单或者取卡密。
- 唯一和外部系统打通的地方在「权益类商品」：这类商品可以挂一个「应用」，应用有网关地址和 APIKEY，买家付款后由平台去请求这个网关。自己建应用要平台另外开权限，新注册的商家账号没有；网关的请求格式也没有公开文档，要找平台客服要。拿到权限和文档以后，可以让本站来当这个网关：买家在那边付款，本站出卡密、记订单。这一步现在没做。

现在做的只有一件事：把买家送到那边的商品页付款。

用法：在后台编辑商品，把那边商品页的地址贴进「站外付款链接」（链动小铺的是 `https://wzyp.cn/item/编号`）。贴浏览器地址栏里最终显示的那个，不要贴短链接，商品页会把链接里的域名写给买家看。链接只收 `https://` 开头的完整地址，不限定是哪个平台。填了以后：

- 商品页的下单面板换成「去付款」按钮，打开这个链接。这件商品不能再在本站下单。
- 首页卡片和商品页不显示本站的库存。
- 本站不生成订单。「查订单」和订单来源里都没有这一笔。
- 在那边收到的钱要手工记进对账：到后台「收支」里，照那边的结算单记「站外收入」和「站外退款」，对账时并进买家付款和退款。按买家实付的数记，平台抽的手续费另记一笔「支付手续费」；日期填买家付款、退款的那天，一周合记一笔时填在那一周里。合作平台的钱提现到谁个人手里，要先转进收款账户再对账：站外收入一律按收款账户里的钱算，也计入挂名补偿的基数。不记的话对账单的利润会偏低，存档又不能撤回；有站外付款的商品而这一周没记站外收入时，对账页会提醒。
- 名称、说明、价格还是在本站后台手工维护，价格要自己和那边保持一致。

两种搭法：

1. **货放在那边。** 卡密上传到那边的商品里，买家付款后直接在那边拿到。本站只当门面。
2. **那边只卖兑换码。** 在后台「兑换码」里生成一批码，当作卡密上传到那边。买家付款拿到码，回本站的「兑换」页取货。货、发货记录、换号、订单来源都还在本站；兑换生成的是 0 元订单，不算买家付款；这部分收入同样照那边的结算单记进「收支」的「站外收入」。

用第二种搭法要注意三件事：

- 买家在那边的订单页只看得到一串 12 位的码。要把本站兑换页的地址写进那边的商品说明，本站商品说明的第一行也写明「付款后拿到的是兑换码，回本站兑换页取货」。
- 每生成一批码就马上复制上传，以前传过的码不要再传一遍。
- 本站的卡密库存不能少于还没兑换的码数。本站一张卡密都不剩、又还有码没兑换时，这件商品会显示售罄并停掉「去付款」，后台概览和商品列表会提醒；补货以后，没兑换成的码还能用。

## 这一版没做的

- 买家注册登录：用「订单号 + 邮箱」查单代替了。
- 真实支付：只有模拟支付和接口，另外可以用站外付款链接把买家送到寄售平台付款。
- 和链动小铺自动同步：它没有通用的开放接口，商品、价格、订单都不会自动同步过来；让本站当它「权益类商品」的发货网关也没做，见上面那一节。
- 邮件通知：发货结果只显示在订单页，工单要自己按邮箱回复。
- 翻页：后台的订单、卡密、兑换码、工单各只显示最近 200～300 条。
- 限流计数存在内存里，重启清零，多进程部署时各算各的。
